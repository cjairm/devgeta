## 1. Domain Context

devgeta installs a coordinated visual environment — terminal emulator, tmux,
Neovim, the two AI coders, and i3 on Linux — all themed Gruvbox dark on a
`#282828` background. [docs/guides/theming.md](../../guides/theming.md) is the
source of truth for how that layer is wired.

**The problem:** there is exactly one theme and no way to change it, but the
project behaves as though there are several.

- `cmd/root.go:52` and `:59` advertise `dg change --theme=... --font=...` in
  the help text every user sees. **No such command is registered** — confirmed
  against every `rootCmd.AddCommand` call in `cmd/`.
- `internal/config/fromFile.go:303` defines `current_theme`. **Nothing reads
  it.**
- `configs/neovim/lua/devgeta/themes/tokyonight.lua` exists, fully written, and
  nothing selects it.
- `ROADMAP.md:30-33` lists the command as planned, including "with background
  image updates" and "persist selections in global config".

theming.md already documents this honestly under "Known gaps" #1, #2 and #4.
This cycle closes those three.

**Design decisions already made** — read both before implementing:

- [ADR-0043](../../decisions/ADR-0043-a-theme-is-a-palette-file-not-a-branch-in-every-template.md)
  — a theme is one palette file; templates consume values, never branch on a
  theme name.
- [ADR-0044](../../decisions/ADR-0044-a-theme-declares-a-wallpaper-it-never-ships-one.md)
  — a theme declares a wallpaper path; devgeta ships no image bytes.

| ------------- | --------------------------------------- | --------------------------------------------------------- |

| **Ghostty**   | `configs/ghostty/ghostty.conf.tmpl`     | same, `palette = N=#RRGGBB` form                          |
| **OpenCode**  | `configs/opencode/opencode.json.tmpl:3` | `"theme": "{{ .Theme }}"`, + `themes/default.json` copied |
| **tmux**      | `configs/tmux/tmux.conf.tmpl:111-161`   | hardcoded hex on 13 lines                                 |
| **Neovim**    | `configs/neovim/init.lua:138`           | hardcoded `require("devgeta.themes.gruvbox")`             |
| **Claude**    | `configs/claude/settings.json.tmpl:3`   | hardcoded `"theme": "custom:default"`                     |

**Leave alone:** `internal/tui/components/styles.go` builds devgeta's own TUI

### The three dead assignments to delete

```
internal/apps/alacritty/alacritty.go:58   theme := "default"
internal/apps/ghostty/ghostty.go:83       theme := "default"
internal/apps/opencode/opencode.go:100    theme := DEFAULT_THEME_NAME
```

`DEFAULT_THEME_NAME` is `internal/apps/opencode/opencode.go:36`, asserted by
`opencode_test.go:607` and used in `permissions_test.go` at lines 45, 1130, 1217. Those call sites need updating, not deleting — the permission tests render
the template and must keep doing so.

### Key existing machinery to build on, not around

- `files.GenerateFromTemplate(tmplPath, dstPath, data)` — every templated
  config already goes through this. The palette rides in as extra `data`.
- `config.GlobalConfig` + `Load()`/`Save()` — `current_theme` lives here
  already. ADR-0030: the config loads once per run and is cached.
  **Any new field on `GlobalConfig` that is not a plain value type must be
  deep-copied in `internal/config/clone.go`.** The cache hands out
  `cloneGlobalConfig(cached)`, and that function's `dst := *src` only covers
  value types; `Shortcuts` is the existing `map[string]string` precedent,
  cloned via `cloneStringMap`. Phase 3's `wallpapers` map is subject to this —
  Step 9 says how.
- `cmd/config_settings.go` — the `Settings` registry, the established pattern
  for a user-settable key with `Default`/`Get`/`Set`/`Unset`. **`current_theme`
  does not become an entry here.** Every entry's `Set` does exactly one thing:
  validate the raw value and assign the field, inside `cmd/config.go:212`'s
  `config.Update`. No entry reconfigures anything, and `dg config set` persists
  whatever `Set` assigned as soon as it returns nil — so a registered
  `current_theme` would make `dg config set current_theme x`
  persist a selection with no palette validation, no app reconfigure, and no
  rollback: the config would claim a theme the machine does not have, which is
  the exact failure Step 5's transaction is built to prevent. The registry
  already refuses a key for this reason — `integrations.rtk_claude_hook` is
  listed in `cmd/config_settings_test.go`'s `knownStateFields` as "a deploy
  record, not a preference … a bare `set` here would desync the recorded flag
  from what's actually deployed". `current_theme` is the same class of value.
  `dg theme set` is its only write path; `dg theme` is its read path.
- `apps.SelectiveConfigurer` (`internal/apps/contract.go:35-49`) — the
  established shape for "a capability only some apps have": a small optional
  interface next to `App`, asserted at compile time in each app that has it
  (`claude.go:51`, `opencode.go:33`) and type-asserted at the call site
  (`cmd/configure.go:97`). Step 5's palette-passing interface copies it rather
  than widening `App`.
- `registry.GetApp(name)` — how `dg theme set` reaches an app to re-run its
  themed configure (Step 5's `ForceConfigureTheme`). Do not hand-maintain a
  second app list. But
  `registry.Names()` is **not** the list to iterate: it returns every
  registered app, installed or not (`registry.go:155-162`, a bare sweep of the
  `factories` map). `registry.Meta[name].ItemType` plus
  `gc.IsInstalledByDevgeta` / `gc.IsAlreadyInstalled` is the installed filter,
  used exactly as `cmd/uninstall.go:83-86` uses it. Step 5 specifies this.
- `config.Update(fn)` (`internal/config/lock.go`) — the locked
  load-mutate-save. `Save()` alone is atomic but not lost-update-safe, so
  writing `current_theme` goes through `Update`, not `Load`/mutate/`Save`.
- `embedded.go` / `ConfigsFS` — `//go:embed all:configs`. Anything added under
  `configs/` enters the binary. This is what ADR-0044's no-images test guards.

### Testing patterns

[docs/guides/testing-patterns.md](../../guides/testing-patterns.md). The traps
that apply directly here:

- Never `alacritty.New()` in a test that calls `ForceConfigure`; use
  `&alacritty.Alacritty{Cmd: mockApp.Cmd, Base: mockApp.Base}`.
- `ForceConfigure` writes real files — isolate **every** path it touches via
  `testutil.SetupCompleteTest` or explicit `paths.Paths.*` overrides restored
  in `t.Cleanup`. The wallpaper setter touches `~/Library` on macOS: it must be
  behind the mocked executor, never a live call.
- `testutil.VerifyNoRealCommands(t, mockApp.Base)` against the **same** base
  the app holds.

### Commands to run tests

This cycle touches `configs/` heavily **and** `internal/config`, which has
dozens of importers. Per CLAUDE.md §6 that is explicitly the "blast radius is
most of the tree" case — the embedded-config tests in the root package read
`configs/`, and the root package is the slow one.

**Verification for this cycle is the full suite. Do not claim a targeted run is
sufficient.**

## 3. Objective

**Make the visual setup devgeta already installs a named, switchable theme
called `default`, driven by one palette file per theme and one command
(`dg theme`), without changing how anything looks.**

"Done" for the cycle as a whole: `dg theme set tokyonight` restyles the
terminal, tmux, Neovim and both AI coders together; `dg theme set default`
returns the machine to the colors it has today.

**What "nothing changes" means, exactly.** Two different bars, because two
surfaces change shape on purpose and cannot be byte-compared:

| Surface                                                                                      | Bar                                                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Alacritty, Ghostty, tmux, i3, `opencode.json`, `settings.json`, `claude/themes/default.json` | **Byte-identical.** Render before and after, `diff`, expect zero output. Templating Claude's `overrides` block substitutes the same hex it holds today, so its rendered output must not move a byte either.                           |
| Neovim `init.lua` + `lua/devgeta/theme.lua`                                                  | **Structural, asserted.** `init.lua:138` becomes `require("devgeta.theme")`; a new shim file appears. Test: the shim loads and resolves to `devgeta.themes.gruvbox` for `default`. `init.lua`'s only permitted diff is that one line. |
| `opencode/themes/default.json`                                                               | **Same resolved colors.** Six `theme` entries (four distinct colors) move into `defs` per ADR-0043; the JSON differs, the colors must not. Test: resolve every `theme` key to a hex and compare against a golden captured beforehand. |

Anything not in the second or third row that differs by a byte is a bug, not
an improvement. Anything in them that changes _color_ is also a bug.

### Step-by-Step

#### Phase 1 — name it and wire it

**Step 1: Capture today's palette as data**

- Create `configs/themes/default.yaml` with `colors:` (classic Gruvbox, from
  `tmux.conf.tmpl` and `opencode/themes/default.json`'s `defs`) and
  `terminal:` (Material, from `alacritty.toml.tmpl`).
- **Both groups define the full role set** — the same keys, different hex.
  `terminal:` is not a partial override of `colors:`; which surface reads which
  group, and why a partial group is rejected, is
  [ADR-0043's group mapping](../../decisions/ADR-0043-a-theme-is-a-palette-file-not-a-branch-in-every-template.md#which-group-each-surface-gets-and-where-that-is-decided).
  Do not restate that mapping here or in a template.
- Add `neovim_module: gruvbox`, the required non-color key — Neovim takes a
  plugin, not colors, so a theme names the module instead
  ([ADR-0043's Neovim prerequisite](../../decisions/ADR-0043-a-theme-is-a-palette-file-not-a-branch-in-every-template.md#what-a-palette-cannot-generate-and-how-that-is-handled)).
  It resolves to `lua/devgeta/themes/<module>.lua`, which for `default` already
  exists.
- **Use the role names in
  [ADR-0043 Decision point 4](../../decisions/ADR-0043-a-theme-is-a-palette-file-not-a-branch-in-every-template.md#decision).**
  That table is the single list: `snake_case` key in the YAML, the same words
  `PascalCase` as the template field (`foreground_muted:` →
  `{{.Palette.ForegroundMuted}}`). Do not introduce short forms like `fg_muted`
  or `bg_hard`, and do not invent roles the surfaces do not use — the table was
  derived from measured usage, including the four roles OpenCode's raw `theme`
  literals need (`border`, `background_subtle`, `diff_added_background`,
  `diff_removed_background`).
- If a surface turns out to need a role the table lacks, add it to the ADR
  table in the same commit. A role named in only one of the two documents is
  the drift this cycle exists to remove.
- Verify: `yq . configs/themes/default.yaml` parses; every hex in the seven
  surfaces appears in the file.

**Step 2: Palette loader**

- `internal/theme/theme.go`, two types because a theme file is not flat and a
  template's data is:
  - `Palette` — one flat hex per role in
    [ADR-0043 Decision point 4](../../decisions/ADR-0043-a-theme-is-a-palette-file-not-a-branch-in-every-template.md#decision)'s
    table. This is what a template consumes and what `ForceConfigureTheme`
    (Step 5) takes.
  - `Definition` — one loaded theme file: `Name`, `NeovimModule`, and the two
    groups. `Load(name string) (Definition, error)` reads from
    `paths.Paths.App.Configs`' themes dir; `List()` enumerates available themes.
- **`Definition.PaletteFor(surface string) (Palette, error)` is the only place a
  group is chosen**, from the one table in
  [ADR-0043's group mapping](../../decisions/ADR-0043-a-theme-is-a-palette-file-not-a-branch-in-every-template.md#which-group-each-surface-gets-and-where-that-is-decided):
  Alacritty and Ghostty get `terminal:`, the other five get `colors:`. Keyed by
  the `pkg/constants` app names (`constants.Alacritty` = `"alacritty"`,
  `pkg/constants/constants.go:100,120,124,133,136,137,149`), so the key is the
  same string `registry.GetApp` and Step 5's themed list already use.
  - A surface with **no table entry is an error**, not a silent fall back to
    `colors:`. An eighth themed surface added without a mapping entry then fails
    its first call rather than quietly rendering the wrong group.
  - `theme.CurrentFor(surface string) (Palette, error)` is the convenience each
    app's `ForceConfigure` wrapper uses (Step 5): resolve `current_theme`, fall
    back to `default` when empty, `Load`, then `PaletteFor(surface)`. An app
    names **itself** — `theme.CurrentFor(a.Name())` — never a group.
- **A theme with no `terminal:` group uses `colors:` for the terminal surfaces
  too.** `Load` resolves that at load time by copying the `colors:` group into
  the terminal slot, so `PaletteFor` never returns a partly filled palette and
  no caller has to know whether the fallback fired. This is the path every theme
  after `default` is expected to take (ADR-0043: new themes SHOULD define only
  `colors:`).
- Validation rejects a missing role or an unparseable color **before** any
  config is written (ADR-0043's last trade-off). It runs over **every group the
  file defines**: `colors:` is required and complete, and `terminal:` — if
  present at all — is held to the same full role set, so a half-written
  `terminal:` is a load error rather than a silent mix of two palettes. The
  error names the group as well as the role.
- Validation also resolves `neovim_module`, looking in **two** trees and
  accepting either (ADR-0043's Neovim prerequisite):
  1. **Shipped** —
     `<paths.Paths.App.Configs.Neovim>/lua/devgeta/themes/<module>.lua`. That is
     the extracted copy of the embedded configs, written by
     `ExtractEmbeddedConfigs` (`embedded.go:60`) on install and after a binary
     upgrade, and it is the same tree `Load` reads the theme YAML out of — so
     checking it costs no dependency the loader does not already have.
  2. **User-supplied** —
     `<paths.Paths.Config.Nvim>/lua/devgeta/themes/<module>.lua`
     (`pkg/paths/paths.go:370`, i.e. `~/.config/nvim`). `files.CopyDir` is
     additive, so a module the user dropped there survives
     `dg configure neovim --force`.

  A module in neither tree rejects the theme here, before any config is written,
  naming both paths it looked in and the modules it found in each.

- **Why both trees, and not the deployed one alone.** Checking only
  `~/.config/nvim` breaks in two ways:

**`dg theme set` is the only path that writes `current_theme`.** It is not
registered in `cmd/config_settings.go` (§2 says why: a registry `Set` validates
and assigns a field and nothing else, so `dg config set current_theme x` would

consequences to implement deliberately rather than discover:

- `dg config get/set/unset current_theme` answer with `cmd/config.go`'s existing
  unknown-key error, which lists the registered keys. That is the same treatment
  `integrations.rtk_claude_hook` already gets, for the same reason. The reason
  goes in a comment on the `CurrentTheme` field in `internal/config/fromFile.go`,
  next to the field, where the next person to consider registering it will read

  field — a `dg config` change, not a theming one. Out of scope here.

**Which apps `set` touches.** `registry.Names()` returns **every registered
app, installed or not** — it is a bare key sweep over the `factories` map
(`registry.go:155-162`), with no installed-state filter anywhere in it.
Calling `ForceConfigure` across that list would write configs for apps the user
never installed. Two filters, both using machinery that already exists:

1. **Themed.** A fixed, **ordered** list of the seven surfaces in §2. It is not
   derivable from `apps.AppKind` (Alacritty and i3 are `desktop`, tmux and
   Neovim are `terminal`, and plenty of apps in both kinds have no theme), so it
   is an explicit ordered list in `cmd/theme.go` — the one place, referenced by
   both `set` and the tests. Ordered, not a set, because the failure tests below
   need to put a specific surface before the one they rig to fail.
2. **Installed.** Copy `cmd/uninstall.go:83-86` exactly: `registry.Meta[name]`

   still one devgeta configures. A skipped app prints one line saying it was
   skipped, exactly as `uninstall` does. Do not hand-maintain a second app

**How the requested palette reaches each app.** `App.ForceConfigure()` takes no
arguments (`internal/apps/contract.go:26`), and every themed app loads the
global config itself inside it: `alacritty.go:49,54`, `ghostty.go:74,79`,
`tmux.go:57,62`, `neovim.go:164,172`, `claude.go:116,125`, `opencode.go:84,97`,
`i3.go:56,66`. An app configured while `current_theme` still holds the old name
therefore renders the **old** theme — `dg theme set` would rewrite seven configs
with the colors they already had and then persist a name nothing on the machine
matches. Writing `current_theme` last (below) is what makes that certain rather
than intermittent; the cause is reading the palette out of the config file at
all during a switch. So the validated
palette is passed in explicitly, through an optional interface next to
`apps.SelectiveConfigurer` in `internal/apps/contract.go` — same shape, same
reason, a capability only some apps have:

```go
// ThemedConfigurer is implemented by the seven apps with a theme surface.
// It exists because ForceConfigure() takes no arguments and resolves the
// palette from current_theme, which `dg theme set` deliberately has not
// written yet (see the cycle doc's Step 5 transaction).
type ThemedConfigurer interface {
    ForceConfigureTheme(p theme.Palette) error
}
```

- Each of the seven apps gains `ForceConfigureTheme(p theme.Palette)` holding
  the body its `ForceConfigure` has today, and `ForceConfigure()` becomes
  `p, err := theme.CurrentFor(a.Name()); ...; return a.ForceConfigureTheme(p)`.
  `theme.CurrentFor` (Step 2) resolves `current_theme` out of the loaded
  `GlobalConfig`, falls back to `default` when it is empty, and hands back the
  flat palette for **that** surface's group. One body, two entry points — no
  duplicated configure logic, and plain `dg configure <app> --force` still
  renders whatever theme the machine is on.
- **The palette an app receives is already the right group.** `dg theme set`
  calls `def.PaletteFor(name)` inside its loop over the themed list; an app's own
  wrapper calls `theme.CurrentFor(a.Name())`. Both go through the single table in
  `internal/theme` (Step 2), so neither `cmd/theme.go` nor any of the seven apps
  contains a `colors:`-versus-`terminal:` decision of its own.
- Each themed app adds `var _ apps.ThemedConfigurer = (*X)(nil)` beside its
  existing `var _ apps.App` assertion, and a test asserts that every entry in
  `cmd/theme.go`'s themed list satisfies the interface. A surface added to that
  list without the method then fails the build or the test rather than a user's
  `dg theme set`.
- **The `App` contract does not change.** The apps with no theme surface are
  untouched, and `dg theme set` type-asserts the same way `cmd/configure.go:97`
  does for `--only`.
- `theme.Palette` is passed by value, already validated by the loader (Step 2),
  so no app re-resolves or re-validates it.

**Rejected alternative: write `current_theme` first and roll that write back on
failure.** It needs no new interface — apps keep reading the config, and the
`{path, modTime, size}`-keyed cache (`internal/config/fromFile.go:341-364`,
refreshed by every `Save`) would hand each app the new value rather than a stale
one. It was rejected because it makes the transaction's core guarantee depend on
an undo succeeding: after a mid-way failure the config has to be written a
second time to restore the old name, and if that second write fails, the config
claims a theme the machine does not have — the exact outcome this transaction
exists to prevent. Passing the palette in keeps the guarantee structural:
nothing on disk names the new theme until every app has succeeded. It also keeps
the apps' own writes out of it — each themed `ForceConfigure` ends in its own
`gc.Save()` (alacritty, ghostty, tmux, neovim, claude, opencode, i3 all do),
saving the config as they loaded it, so with the palette passed in they can only
ever write back the old name, never a half-committed new one.

**What happens when one app fails.** Any of the seven can fail — a missing
template after a stale-binary install, a permission error, a full disk. To undo
a failure, the transaction backs up **the exact paths that app's themed
configure writes**, not "its config directory". Those are not the same
thing: only one of the seven writes a directory devgeta owns outright, and one
does not write into a config directory at all.

| Surface       | Back up                                                  | Why that, and not the config dir                                                                                                                                                                                                                                                                                                                       |

| **Ghostty**   | file `~/.config/ghostty/config`                          | Same shape (`ghostty.go:25`'s `ghosttyConfigFileName` is `config`)                                                                                                                                                                                                                                                                                     |
| **OpenCode**  | dir `~/.config/opencode`                                 | The one true directory case: `opencode.go:85` `os.RemoveAll`s the whole directory and repopulates it, so the whole directory is already at stake                                                                                                                                                                                                       |
| **tmux**      | file `~/.tmux.conf`                                      | The themed output is a **home-directory file** (`tmux.go:70`, `Paths.Home.Root` + `.tmux.conf`), not a directory. `paths.Paths.Config.Tmux` is declared in `pkg/paths/paths.go:373` but **nothing reads it** — backing it up is a no-op                                                                                                                |

A directory-only transaction is wrong in both directions, which is why the
manifest is per-path: tmux could not be restored at all, and removing a
directory backup on success (step 6) would delete every user file in the five
directories `ForceConfigure` does not repopulate — including the user-added
Neovim theme modules Step 2 explicitly relies on surviving
`dg configure neovim --force`.

Order and outcome:

1. Load the `Definition` for `<name>` and validate it **before touching
   anything** (Step 2). An unknown or malformed theme exits here, having written
   nothing — §6's manual check 6.
2. **Record that a switch is in progress**, before the first backup exists:
   one `config.Update` setting a new `pending_theme: <name>` field and leaving
   `current_theme` alone. Nothing renders from this field — see "Why a phase
   record is needed" below for what it is for and why it is not the rejected
   write-`current_theme`-first alternative. If this write fails, exit here:
   nothing has been backed up or configured.
3. For each themed installed app, in the fixed list order, back up every
   manifest entry it owns, then
   `ForceConfigureTheme(def.PaletteFor(<app name>))` — the flat palette for that
   surface's group (Step 2). Back up by
   renaming aside —
   `<path>.dg-theme-backup`, a file exactly like a directory. An entry that does
   **not exist yet** (a fresh machine has no `~/.tmux.conf`) is recorded instead
   by creating an empty `<path>.dg-theme-absent` marker: "restore" for that
   entry means delete, and a rename-aside of a missing path cannot say so.
4. On the **first** failure, stop. Undo every entry backed up so far —
   including the failed app's — by renaming its backup back, or deleting the
   path where an absent marker sits. Then clear `pending_theme` and return the
   error. Do not continue through the remaining apps: a half-themed machine is
   the outcome §4's atomicity rule exists to prevent, and it is also the one a
   user cannot easily diagnose.
5. **`current_theme` is written last, only after every app succeeded**, through
   `config.Update` (`internal/config/lock.go:58`) so the load-mutate-save is
   locked. Persisting first and configuring second is the ordering the finding
   caught: a failure after persistence leaves the config claiming a theme the
   machine does not have.

   **The commit sets `current_theme` and clears `pending_theme` in the same
   `config.Update` call** — one `fn`, one save. `updateLocked` runs `fn` and then
   calls `gc.Save()` exactly once (`internal/config/lock.go:101-107`), and `Save`
   goes through `writeGlobalConfigFile` to `files.WriteFileAtomic`
   (`internal/config/cache.go:152-156`, `pkg/files/files.go:236`) — a temp file
   plus rename — so both fields change in one rename. There is no instant on disk where
   `current_theme` is the new name and `pending_theme` is still set. That is what
   makes the commit a single point rather than a two-write window, and it is why
   the phase record needs no atomicity mechanism of its own.

   **That final write can itself fail, and it rolls back exactly like step 4.**
   `config.Update` has three failure exits: the sidecar lock (`MkdirAll`,
   `OpenFile`, a non-`EWOULDBLOCK` flock error, or the 10-second
   `lockAcquireTimeout` — `pkg/files/lock.go:58-110`,
   `internal/config/lock.go:24`); a load error that is not `os.IsNotExist`
   (`lock.go:90-92`); and `gc.Save()` (`lock.go:104`). In all three the
   persisted `current_theme` keeps the **old** name — `Save` is temp-file plus
   rename, so a failed save leaves the previous file whole — while every surface
   it configured already holds the new one on disk. That is the same incoherence
   inverted,
   and it is undoable, because the backups and absent markers from step 3 are
   still on disk: step 6 has not run yet. So on a commit failure, undo every
   manifest entry the way step 4 does, then return the error. Do not retry the
   commit — a lock timeout means another devgeta process is writing the config,
   and a second attempt races it.

   Clearing `pending_theme` is part of that undo and can fail for the same
   reason the commit did. It does not have to succeed: a `pending_theme` left
   set with no backups on disk is exactly the state recovery handles by clearing
   it and restoring nothing (see below).

   **No live push has happened yet at that point, and that is what makes the
   commit failure recoverable.** Step 7 is ordered after commit precisely
   because a live push cannot be rolled back (see the next block), so a commit
   failure lands before tmux's `ApplyLiveTheme` has run: files, `current_theme`
   and the running tmux server all end up back on the old theme together. Any
   change that moves a live push earlier than step 7 reopens exactly the
   file-versus-live-server disagreement the next block exists to close.

6. On success, remove the backups and the absent markers.
7. Only then, apply the theme to anything **live** — see the next block. This
   step is outside the transaction and best-effort.

Rename-aside/rename-back is the mechanism, not copy: it is atomic per entry and
cannot half-restore. The backup is always a **sibling** of the path it shadows,
which keeps it on the same filesystem — a backup collected under
`~/.config/devgeta/` could be on another mount, where `os.Rename` fails with
`EXDEV`.

**Why a phase record is needed: backups alone do not say which way to recover.**
A crash leaves backups and markers on disk, so `dg theme set` sweeps the
manifest on entry, before anything else, and says what it did — and so do
`dg configure` and `dg install`, for the reason given below. But the sweep
cannot be an unconditional restore, because backups outlive the commit: step 5
writes `current_theme` and step 6 removes the backups, so a crash in between
leaves a committed switch with its backups still lying around. Restoring those
would roll every deployed file back to the old theme while `current_theme` names
the new one — the same file-versus-config incoherence the rest of this
transaction is built to avoid, just reached by a different route. The sweep has
to know which phase the dead attempt died in, and only something durable can
tell it.

`pending_theme` is that record, and the ordering is what makes it sound:

- It is **set before the first backup is taken** (step 2) and **cleared by the
  commit itself** (step 5), in the same single rename that writes
  `current_theme`. So a backup on disk always sits in exactly one of two states,
  with no third: `pending_theme` set → the attempt never committed;
  `pending_theme` empty → it did.
- Recovery therefore reads one field and has no decision to make:

  | On entry                              | Recovery does                                                                          |
  | ------------------------------------- | -------------------------------------------------------------------------------------- |
  | `pending_theme` set, backups found    | Restore every backup, delete every path holding an absent marker, clear the field.     |
  | `pending_theme` set, no backups found | Nothing to restore — clear the field. (A crash in step 2/3, or a failed step-4 clear.) |
  | `pending_theme` empty, backups found  | The attempt committed. **Delete** the backups and markers; restore nothing.            |
  | `pending_theme` empty, no backups     | Nothing to do.                                                                         |

- **Nothing in the run may write the field back out stale.** Every themed
  `ForceConfigure` ends in its own `gc.Save()`, saving the config as it loaded
  it, so a `GlobalConfig` read before step 2 and saved after it would drop
  `pending_theme` — leaving "no pending, backups present", which recovery reads
  as committed and would clean up under a `current_theme` that is still the old
  name. Two rules keep that impossible: step 2 is the run's **first** config
  write, before any app configure loads a config; and `dg theme set` never saves
  the `GlobalConfig` it loaded for the installed filter. Loads after step 2 see
  the field, because `writeGlobalConfigFile` refreshes the read cache on every
  write (`internal/config/cache.go:152-170`).
- **The sweep needs no list from the dead run.** The manifest is the fixed
  per-surface table above, so recovery walks those paths and looks for a
  `.dg-theme-backup` or `.dg-theme-absent` sibling of each — installed-app
  filtering does not enter into it, because a sibling exists only where the dead
  run actually created one.
- A half-finished step 6 is fine in both directions: removing backups is
  idempotent, and a second crash during recovery lands the next run in the same
  table.
- It is **not** the rejected "write `current_theme` first" alternative.
  `pending_theme` is never a theme selection: no template, no app, and no
  palette lookup reads it. `theme.CurrentFor` resolves `current_theme` only, so
  an app configured mid-switch still cannot render the name being switched to —
  the palette still arrives as an argument. The field records a transaction
  phase, nothing more.
- It goes on `GlobalConfig` beside `CurrentTheme`
  (`internal/config/fromFile.go:298-311`) as `pending_theme,omitempty` — a plain
  string, so `cloneGlobalConfig`'s `dst := *src` already covers it and no
  `clone.go` code changes; add it to that function's trailing comment listing
  the value-type fields, which names `CurrentTheme` today. Like `current_theme`
  it is **not** a `cmd/config_settings.go` key, for the same reason: it is
  transaction state, not a preference.

**The sweep runs on entry to every command that writes a manifest path, not
only `dg theme set`.** `cmd/configure.go`'s `runConfigure` knows nothing about
theme state: it refreshes the embedded tree and calls `app.ForceConfigure()`
(`cmd/configure.go:75-133`, force branch at `:119-120`) straight onto the same
paths the manifest holds. So a crash mid-`set` followed by an ordinary
`dg configure tmux --force` loses the user's work silently — the `--force`
writes a fresh `~/.tmux.conf` while `~/.tmux.conf.dg-theme-backup` is still
lying beside it, and the next `dg theme set`'s sweep renames that backup back
over the new configuration. `dg install` reaches the same paths through each
category coordinator's `SoftConfigure`
(`internal/tooling/desktop/desktop.go:351-361` for i3), where the absent-marker
case is worse still: the real path was renamed aside, so `SoftConfigure`'s
marker-file check (`internal/apps/i3/i3.go:73-79`) sees nothing, writes a full
config, and the sweep then deletes it.

So the sweep is an exported function in `internal/theme` —
`RecoverInterrupted()` — and it is the first thing after flag parsing in
`dg theme set`, `dg configure` and `dg install`:

- It is **safe to call anywhere**, which is what makes this cheap. It reads one
  field, walks the fixed manifest looking for `.dg-theme-backup` /
  `.dg-theme-absent` siblings, and in the ordinary case finds none and returns
  having touched no file. No config write happens unless `pending_theme` is set
  or a sibling exists.
- It runs **before** the command's own work, so `dg configure` writes onto a
  tree with no backups beside it. After the sweep there is nothing left for a
  later `set` to restore — that is what closes the interleaving, rather than
  detecting it afterwards.
- **If the sweep fails, the command stops and returns that error.** Configuring
  on top of a half-restored manifest is the damage; proceeding would bury it.
- **What the user sees** — one line before the command's normal output, so
  filesystem work is never invisible:
  - restored: "recovered an interrupted switch to tokyonight: restored 4 config
    paths — run `dg theme set tokyonight` to retry"
  - cleaned up (the committed case): "cleaned up 4 leftover backups from a
    completed switch to tokyonight"
  - nothing found: no output at all.

**Rejected: refusing the command while `pending_theme` is set.** It is the
obvious guard and it is worse. It locks the user out of `dg configure` and
`dg install` until they run a theme command, and the state it refuses on is one
a user reaches by pressing Ctrl-C. Recovery is idempotent and needs no input
from anyone, so there is nothing to ask about.

**Rejected: `cmd/root.go`'s `PersistentPreRunE`.** One choke point every
subcommand passes through (`cmd/root.go:96`, which today only calls
`logger.Init`) would make a forgotten call site impossible, which is what §4
prefers. Rejected anyway: it would have read-only commands (`dg theme list`,
`dg config get`) and the hook-invoked `dg task` paths renaming files as a side
effect of running at all. The three call sites get a test instead —
`TestRecoverInterruptedRunsOnEveryConfigWriter` asserts each of the three
`RunE`s calls the sweep, through a package-level `recoverInterruptedFn` var the
test swaps for a spy, the same override pattern `cmd/configure.go:25` and `:34`
already use for `getAppFn` and `refreshEmbeddedConfigs`. A fourth command that
deploys configs without the call then fails that test rather than a user's
files.

**One surface pushes the theme into a running process, and that push has to wait
for commit.** `tmux.ForceConfigure` sources the file it just wrote into the live
server when `TMUX` is set — `internal/apps/tmux/tmux.go:79-82`,
`_ = t.ExecuteCommand("source-file", configDest)`. Inside the transaction that
is unrecoverable: rollback restores `~/.tmux.conf`'s bytes, but the running
server keeps the colors it was told to load, so a later app's failure leaves the
live session on the new theme while every file and `current_theme` are back on
the old one. Re-sourcing the restored file on rollback fixes only half of it —
on a fresh machine with no `~/.tmux.conf` the absent-marker path deletes the
file, leaving nothing to source, and tmux offers no way to return a `set -g`
option to whatever the server held before.

So the live push moves out of the transaction:

- `ForceConfigureTheme` writes files and nothing else; tmux's `source-file` does
  not run from it. The reload stays in the wrapper: tmux's `ForceConfigure`
  resolves the palette, calls `ForceConfigureTheme`, then calls its own
  `ApplyLiveTheme` — so plain `dg configure tmux --force` behaves exactly as it
  does today, out of one copy of the reload code.
- Live application becomes a second small optional interface in
  `internal/apps/contract.go`, implemented today by tmux alone:

  ```go
  // LiveThemeApplier is implemented by a themed app that can push a theme
  // into an already-running process. `dg theme set` calls it only after its
  // transaction has committed, because a live push cannot be rolled back.
  type LiveThemeApplier interface {
      ApplyLiveTheme() error
  }
  ```

  Tmux's implementation is the call `tmux.go:79-82` makes today: gated on
  `TMUX`, routed through the existing `ExecuteCommand` wrapper (CLAUDE.md §6 —
  external tools go through their app wrapper).

- `dg theme set` calls it on each surface it configured, after step 6. A failure
  **warns and rolls nothing back**: the files and `current_theme` are already
  committed and correct, and a stale live session is fixed by starting a new
  one. Same best-effort stance tmux already takes with its own `_ =`, and the
  same one Step 9 gives the wallpaper.

**Audit — tmux is the only one of the seven.** Every themed app's
`ForceConfigure` was read for a call that pushes state into a running process:
alacritty (`:49`), ghostty (`:74`), neovim (`:164`), claude (`:116`), opencode
(`:84`) and i3 (`:56`) write files and update the global config only. The single
exec anywhere in those paths is neovim's `nvim --version` (`neovim.go:257`), a
read-only query. Where a running app picks a change up by watching its own
config file, that is the app reading the path rather than devgeta pushing, so it
follows whatever bytes sit at the path after a rollback exactly as it followed
the write. Surfaces that read their config only at startup (Neovim, both AI
coders) show the new theme in processes started after the switch — not a
transaction hole. If a later change makes another surface push to a live
process, it implements `LiveThemeApplier` rather than doing it inside
`ForceConfigureTheme`.

**The rollback covers theme state only, on purpose.** `ForceConfigureTheme` also
re-deploys things that do not vary by theme — `starter.sh`, Claude's hook
scripts and `lib/`, OpenCode's `plugin/`, the shared skills/commands/agents —
and re-records installed state via `gc.Save()` / `RegenerateShellConfig`. Those
are idempotent re-writes of identical content, so they stay outside the backup
and a rollback leaves them as the configure call left them. If a future change
makes any of them theme-dependent, it belongs in the manifest.

**Step 6: Guard rails**

- `embedded_test.go`: **no file under `ConfigsFS` is an image, checked by
  content and not by name** — `TestEmbeddedConfigsShipNoImageBytes`, the guard
  ADR-0044 point 2 rests on. `fs.WalkDir` over `ConfigsFS` (package `main`, so
  the test belongs in the root package), `fs.ReadFile` each file, and fail on
  either signal:
  - `http.DetectContentType(data)` returns a type starting `image/`. It sniffs
    the leading 512 bytes and covers PNG, JPEG, GIF, WebP, BMP and ICO —
    stdlib, so no new dependency (§6).
  - the name carries a raster extension (`.jpg`, `.jpeg`, `.png`, `.gif`,
    `.webp`, `.bmp`, `.ico`, `.tiff`, `.heic`, `.avif`) even when the bytes do
    not sniff as one. A truncated or empty file named `logo.png` is still an
    image asset landing in the tree, and these extensions cover the formats the
    sniffer does not know.

  A name-only check — the earlier plan — does not enforce the invariant at all:
  an image committed as `wallpaper.dat`, or with no extension, passes it
  untouched. The sniff is what makes the rule structural (§4); the extension
  list is a cheap second net, not the primary check. All 160 files under
  `configs/` today are text (`file --mime-type` over the tree: `text/*` and
  `application/json` only), so the guard starts green and needs no exemption
  list.

- **Prove the guard bites**, or it is decoration: a sub-test runs the same check
  over an in-memory `fstest.MapFS` holding a real 1×1 PNG's bytes under the name
  `notes.txt`, and asserts it is flagged. That is the exact case the extension
  check misses, so the check takes an `fs.FS` parameter rather than reading
  `ConfigsFS` directly.
- **Bounded limit, recorded rather than implied.** A format outside Go's sniff
  table (AVIF, HEIC, TIFF; an SVG sniffs as text) carrying an extension that is
  not on the list either would still pass both nets. Left open deliberately:
  closing it means a decoder per format, a new dependency (§6) for a case no
  commit has produced. ADR-0044 point 2 states the invariant to that bound and
  not as an absolute.
- `embedded_test.go`: no value in a shipped OpenCode theme's `theme` block is a
  literal color — every one is a `defs` key (ADR-0043). The `light` halves are
  the recorded exception and the test exempts them by name, not by pattern, so
  a new literal cannot slip in under the exemption.
- Goldens matching §3's bars: byte goldens for the seven byte-compared outputs,
  a resolved-color golden for OpenCode's theme JSON, and an assertion that the
  Neovim shim loads and names `devgeta.themes.gruvbox` for `default`.
- **Rendered goldens for the group mapping**, one per surface, from a fixture
  theme whose `colors:` and `terminal:` disagree on every role: Alacritty's and
  Ghostty's rendered configs contain the `terminal:` hex and none of the
  `colors:` hex, and tmux's, Neovim's, OpenCode's, Claude's and i3's contain the
  `colors:` hex and none of the `terminal:` hex. Step 2's `PaletteFor` tests pin
  the table; these pin that each app actually asks for its own group, which a
  unit test on the table alone cannot see. For `default` the byte goldens above
  already catch a swap — its two groups differ — but that stops being true for
  any single-group theme, which is why the fixture is separate.
- Verify: **full** `go test ./...`

**Step 9: Persistence first, then the setter.**

Where the path lives is the part that has to be settled before any code, per
[ADR-0044 point 3](../../decisions/ADR-0044-a-theme-declares-a-wallpaper-it-never-ships-one.md#decision):

- **`GlobalConfig` gains `wallpapers map[string]string`
  (`yaml:"wallpapers,omitempty"`), keyed by theme name.** Not the theme YAML:
  `configs/themes/*.yaml` is embedded, and `ExtractEmbeddedConfigs`
  (`embedded.go:60`) does an unconditional `os.WriteFile` over every embedded
  file on install and after a binary upgrade, so a path written into a shipped
  theme file is erased on the next upgrade with no warning.
- **The new map has to be deep-copied, in the same commit that adds it.**
  `internal/config/clone.go` is the other half of ADR-0030's cache contract: the
  cache hands out `cloneGlobalConfig(cached)`, whose `dst := *src` gives
  independent storage only to value types. An un-cloned `Wallpapers` map would
  be shared between the cache and every caller, so one caller's write would
  silently mutate what the next `Load()` returns. Two edits:
  - `cloneGlobalConfig`: `dst.Wallpapers = cloneStringMap(src.Wallpapers)` —
    the same helper `Shortcuts`, the existing `map[string]string` field, already
    uses. Update the comment listing which fields the shallow copy covers; it
    names `CurrentTheme` and friends today.
  - `clone_test.go`: add a `Wallpapers` entry to
    `newFullyPopulatedGlobalConfig`. `TestCloneGlobalConfig_DeepCopiesEveryReachableField`
    perturbs by reflection and does handle maps, but it can only perturb what
    the fixture populated — leave the field out of the fixture and the guard
    passes on a nil map while the real aliasing bug ships. The fixture is the
    guard; that is why its doc comment requires every field to be non-zero.
  - Verify: `go test ./internal/config/` — and confirm the guard bites, by
    running it once with the `cloneGlobalConfig` line omitted and seeing it
    fail.
- **`dg theme set-wallpaper <path>`**: validate the file exists and is a
  readable image, copy it into `~/.config/devgeta/wallpapers/` under the
  content-addressed name below, then `config.Update` to set
  `wallpapers[<current theme>]` to the copied path. Never store the argument
  path — the copy is the whole point (ADR-0044). With no `current_theme` set,
  key it under `default`, the same fallback the palette loader uses.
- **The destination name comes from the file's bytes, not its basename:**
  `wallpapers/<first 16 hex chars of the SHA-256><ext>`, `<ext>` being the
  source's lowercased extension. Naming the copy after the basename is broken:
  two different images both called `wallpaper.jpg`, set for `default` and for
  `tokyonight`, resolve to the same destination, and `files.CopyFile` overwrites
  it (`os.WriteFile`, `pkg/files/files.go:64`). Both map entries would then
  point at one file holding the second image — exactly the cross-theme bleed the
  bullet below promises cannot happen. Content addressing makes that impossible
  rather than documenting it (§4):
  - Distinct bytes always get distinct names, whatever the sources were called.
    16 hex characters is 64 bits; for a directory holding a handful of images
    an accidental collision is not a real risk.
  - Identical bytes get one name, so one image set for two themes is one file
    with two entries pointing at it. That is correct sharing, not a collision —
    each theme still resolves to the image it was given.
  - The name implies the content, so a name that already exists already holds
    the right bytes: skip the copy. Re-setting the same image rewrites nothing.
  - Write it with `files.WriteFileAtomicFrom` (`files.go:245`), not
    `files.CopyFile`: an interrupted `CopyFile` leaves a truncated file under a
    name claiming to be a whole image, and the skip rule above would trust it
    from then on.
  - The two alternatives were weighed and dropped. `<theme>-<hash>` stores the
    bytes twice when two themes share an image, and puts a theme name — read
    from `current_theme`, which a user can hand-edit — into a filesystem path.
    `wallpapers/<theme>/<basename>` has that same path-segment problem and still
    overwrites within a single theme.
- **A superseded copy is deleted, or the directory grows without bound.** After
  the `config.Update` commits, sweep `wallpapers/`: remove every file whose name
  matches the content-addressed shape (`^[0-9a-f]{16}\.[a-z]+$`) that no value
  in the post-commit `wallpapers` map points at. The shape check is what stops
  the sweep from deleting a file the user put in that directory themselves.
  It runs after the commit and is best-effort — a failed removal warns, it does
  not fail the command, because the recorded path is already correct.
- **`dg theme set <name>` applies `wallpapers[<name>]` when that key exists,
  and otherwise leaves the desktop alone** — it never clears a wallpaper set
  outside devgeta and never carries one theme's image onto another. A theme
  file's own `wallpaper:` key is a declared default, consulted only when the
  map has no entry for that theme.
- The wallpaper step runs **after** Step 5's config transaction has committed,
  and its failure warns rather than failing the command (ADR-0044 point 4). It
  is therefore outside the rollback: a theme switch whose wallpaper did not
  apply is a themed machine with a warning, not a rolled-back one.
- Then the setter itself: one interface, macOS impl on the route Step 8
  measured, `feh --bg-fill <path>` on Linux.
- **The setter's helper binary is an optional prerequisite** (ADR-0044
  point 6), and the probe is part of this step rather than an afterthought.
  `feh` is not in devgeta's install set — nothing in `pkg/constants`,
  `package_mappings.go`, `internal/apps/i3/i3.go` or `configs/i3/config`
  mentions it — so the unavailable case is the normal one on a fresh machine,
  not an edge:
  - Before invoking, `commands.LookPathFn("feh")` — the package var at
    `internal/commands/base.go:27`, already used this way for `fc-list` at
    `base.go:275`, so a test can point it at a stub without touching PATH.
  - Not found → warn naming the binary and the install command
    (`sudo apt install feh`), leave the desktop alone, and let `dg theme set`
    finish successfully. Silence here is the failure ADR-0044 point 6 exists to
    prevent: the Linux path would otherwise do nothing with no explanation.
  - Found → invoke through the shared executor's `ExecCommand`, so the mocked
    executor records it (tests below) and the timeout and error-wrapping
    behavior match every other external call. `feh` has no app wrapper and is
    not an i3 subcommand, so the setter is the boundary that shells out; if a
    `feh` wrapper ever exists, CLAUDE.md §6 routes this through it instead.
  - The macOS impl takes the same two branches for whatever binary Step 8's
    route needs. If AppleScript wins, `osascript` ships with the OS and the
    probe is trivially satisfied.
- Register `wallpapers` handling in `cmd/config_settings.go`? **No** — it is a
  map keyed by theme, not a scalar user-settable key; `dg theme set-wallpaper`
  owns it.
- Tests: the setter goes through the mocked executor, never a live call — it
  touches `~/Library` on macOS. Isolate `paths.Paths.Config.Root` so the
  `wallpapers/` copy lands in the sandbox. Cover the naming rule directly:
  - Two **different** images that share a basename (`a/wallpaper.jpg` for
    `default`, `b/wallpaper.jpg` for `tokyonight`) → two files in
    `wallpapers/`, two different map values, and each file's bytes equal to its
    own source.
  - The **same** image set for two themes → one file, two equal map values.
  - The same image set twice for one theme → still one file, unmodified
    (compare mtime), proving no churn.
  - The sweep removes the file a replaced entry orphaned and leaves an
    unrelated file in the directory alone.
  - `TestWallpaperSetter_HelperMissing_WarnsAndSucceeds` — `LookPathFn` stubbed
    to return an error: the mocked executor records no call at all, the
    command's error is nil, and the warning names both the binary and the
    install command. Restore `LookPathFn` in `t.Cleanup`.
  - `TestWallpaperSetter_HelperPresent_InvokesIt` — `LookPathFn` stubbed to
    succeed: the executor records exactly one `feh --bg-fill <copied path>` and
    nothing else.

    pre-crash `~/.tmux.conf` over it (Step 5's sweep on entry)

### Regression Check

- `dg install --help`, `dg version`, `dg configure git` still work
- A **fresh** `dg configure alacritty --force` on a machine with no
  `current_theme` set produces today's config (empty → `default` fallback)
- `dg configure claude --force --only=skills` still works — the AI coders'
  `--only` parts must not regress
- `internal/apps/opencode/permissions_test.go` still passes: it renders the
  template directly and is the test that fails the build on agent asymmetry
- Rebuild before deploying — `dg configure` extracts configs from the running
  binary (CLAUDE.md §12), so a stale binary silently deploys stale templates

## 7. Risks & Trade-offs

| Risk                                                              | Likelihood | Mitigation                                                                                                                                                                                                                                                            |
| ----------------------------------------------------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Rewriting 7 configs silently changes someone's colors             | **High**   | §3's per-surface bar, checked in Steps 3–4 + goldens (Step 6)                                                                                                                                                                                                         |
| `dg theme set` half-applies and leaves a mixed machine            | **High**   | Step 5: validate first, back up and restore the exact paths each app writes, persist `current_theme` last, and roll the whole manifest back if that persist itself fails                                                                                              |
| A crash between commit and cleanup rolls a committed theme back   | Med        | Step 5: `pending_theme` records the phase, set before the first backup and cleared by the commit's own write, so recovery deletes committed backups instead of restoring them                                                                                         |
| A surface renders the wrong color group of a two-group theme      | Med        | Step 2: one surface→group table in `internal/theme`, `PaletteFor` the only chooser, with the per-surface rendered goldens in Step 6                                                                                                                                   |
| Apps render the old theme because `current_theme` is written last | **High**   | Step 5: the validated palette is passed in through `apps.ThemedConfigurer`, never read from the config inside a configure call                                                                                                                                        |
| Rollback leaves a live tmux server on the new theme               | Med        | Step 5: the `source-file` push leaves the themed path and runs only after commit, via `apps.LiveThemeApplier`                                                                                                                                                         |
| Rollback or backup cleanup destroys unrelated user files          | Med        | Step 5's per-path manifest — named files, never `~/.claude` or `~/.config/nvim` wholesale                                                                                                                                                                             |
| `dg theme set` writes configs for apps the user never installed   | Med        | Step 5's installed filter, the same `registry.Meta` + `IsInstalledByDevgeta` pair `dg uninstall` uses                                                                                                                                                                 |
| A second path persists `current_theme` without reconfiguring      | Med        | Step 5: not a `dg config` registry key, so `dg theme set` is the only writer                                                                                                                                                                                          |
| Wallpaper path recorded where an upgrade erases it                | Med        | ADR-0044 point 3 / Step 9: it lives in `global_config.yaml`, never in an embedded theme file                                                                                                                                                                          |
| `wallpapers` map aliased through the config cache                 | Med        | Step 9: cloned with `cloneStringMap`, fixture populated so the reflection guard covers it                                                                                                                                                                             |
| macOS wallpaper route is unverified                               | **High**   | Step 8's live measurement was skipped this pass (maintainer's call); the setter is implemented from documented AppleScript behavior only. Best-effort semantics cap the damage regardless, but this still needs a real Space-switch/logout check before being trusted |
| Brave turns out to be impossible without admin                    | Med-High   | Already timeboxed as a spike with no implementation commitment                                                                                                                                                                                                        |
| Neovim shim breaks `init.lua` for existing users                  | Med        | Fixed-name require; test the generated shim loads                                                                                                                                                                                                                     |
| Validation rejects every theme on a machine without Neovim        | Med        | Step 2 resolves `neovim_module` in the shipped tree as well as the deployed one, so a shipped theme validates before Neovim is installed                                                                                                                              |
| i3 `config` → `config.tmpl` rename breaks Linux installs          | Med        | Untestable on macOS — needs a real Debian/Ubuntu check before merge                                                                                                                                                                                                   |
| Palette role set proves incomplete mid-cycle                      | Med        | Step 1 derives roles from actual usage, not invention                                                                                                                                                                                                                 |
| `permissions_test.go` asymmetry guard trips                       | Low        | Both AI coders change in the same step, never one alone (§12)                                                                                                                                                                                                         |
| Full-suite cost discourages running it                            | Low        | §2 states plainly that targeted runs are insufficient here                                                                                                                                                                                                            |

### Trade-offs Made

- **Two color groups in `default.yaml`** rather than one converged palette —
  keeps Phase 1 visually null. ADR-0043.
- **Two new optional interfaces instead of a wider `App` contract, and instead
  of persisting `current_theme` first.** `ForceConfigure()` takes no arguments,
  so the seven themed apps each grow a `ForceConfigureTheme(p)` that their
  `ForceConfigure` delegates to, and tmux grows an `ApplyLiveTheme()`. The cost
  is one extra method on those apps and a second entry point per app to keep
  correct. Bought with it: the palette never has to be read back out of a config
  file that has not been written yet, and nothing on disk or in a running
  process names the new theme until the transaction commits — so rollback needs
  no compensating write of its own. The alternative (write `current_theme`
  first, undo it on failure) is written out in Step 5 with the reason it lost.
- **A `pending_theme` field in `global_config.yaml` instead of an inferred
  recovery rule.** A crash between the commit and the backup cleanup leaves
  backups on disk that must be **deleted**, while a crash before the commit
  leaves backups that must be **restored**; the files alone cannot say which,
  so something durable has to. The cost is a second theme field users will see
  in their config, normally absent (`omitempty`) and only present while a switch
  is mid-flight. Bought with it: recovery reads one field instead of guessing,
  and it needs no new write mechanism — it is set and cleared by the
  `config.Update` calls the transaction already makes. Step 5.
- **Full suite as the verification gate** rather than targeted runs — the
  `configs/` + `internal/config` blast radius leaves no honest alternative.
- **Wallpaper is best-effort**, a narrow exception to §4's atomicity rule,
  accepted only because it is cosmetic and external. ADR-0044.
- **Fonts deferred** despite being the same shape and a cheap add-on — risk
  management, not oversight.
- **`current_theme` is not readable or writable through `dg config`** — it is
  deploy state, so it gets the same refusal `integrations.rtk_claude_hook`
  already gets. The cost is that a user who sees the key in
  `global_config.yaml` and tries `dg config get current_theme` is told it is not
  a setting rather than being shown the value; `dg theme` shows it. The
  alternative — a registry entry whose `Set` just returns "use `dg theme set`" —
  is expressible in the `Setting` struct but fails
  `TestSettingsRegistry_EveryKeyResolvesToARealYAMLTagPath` on the unprefixed
  key, so it costs a `dg config` change of its own. Step 5.
- **`dg theme`, not `dg change --theme`** — the root help's phantom command
  gets corrected rather than implemented, because a dedicated noun command
  matches `dg config` and `dg wt`. Chosen by the maintainer during planning.

## Notes for Implementers

- **The Phase 1 success criterion is that nothing _looks_ different.** §3 says
  exactly which surfaces must be byte-identical and which two change shape on
  purpose. For everything in the first row, a rendered config that differs by a
  byte is a bug, not an improvement — even if the new color looks better. For
  the two exceptions, a changed _color_ is the bug, and the structural change
  itself must be asserted rather than tolerated.
- **Commit per surface**, not per phase. Seven configs in one commit is
  unreviewable.
- **Rebuild before every manual check.** `dg configure` reads templates out of
  the running binary.
- **Both AI coders move together, always** (§12). `permissions_test.go` fails
  the build on asymmetry and must not be weakened to land anything here.
- **Stop at the Phase 3 and Phase 4 checkpoints** for re-approval rather than
  rolling straight through.
